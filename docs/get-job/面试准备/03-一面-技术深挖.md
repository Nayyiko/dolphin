## 一、开场：项目深挖（会占一半时间）

入口是简历（`01` 的 bullet）。面试官会顺着项目追：

- "讲讲 Dolphin 的整体架构" → 三角色图：Gateway（API 面）→ Scheduler（控制面：etcd 选主 → Informer → WorkQueue → Reconcile → 分发）→ Worker（执行面：协程池 → 执行 → 上报）。配套 etcd/MySQL/Redis。
- "为什么选 etcd 做选主，不用 Redis 锁？" → P1-B2：Lease 过期后旧主写入被拒（ErrLeaseNotFound），Redis 锁做不到，机制上防脑裂。
- "调度延迟 1.4s 从哪来的？" → P1-B1：Informer 1s 轮询间隔。
- "Worker 挂了任务怎么恢复？" → P1-B3：心跳滑动窗口 + 幂等 instance_id。
- "这套系统哪些是真难点？" → 假脑裂排障（观测 vs 系统）+ 失权即停（onLoseLeader 取消 leader 循环）。

> 深挖弹药全部在 `01`，每条 bullet 有 30 秒讲法和追问兜底。

## 二、Go 语言与并发（高频必考）

| 考点 | 高频问法 | 贴回 Dolphin 怎么讲 |
|------|---------|-------------------|
| GMP 调度 | GMP 是什么？goroutine 怎么调度的？ | Dolphin 的 Worker 用协程池并发执行任务——我能讲 GMP 的 M 与 P 绑定、本地队列、work stealing |
| GC | Go GC 原理？三色标记？ | 讲三色标记 + 写屏障；"内存逃逸"：Dolphin 里什么对象会逃逸到堆上 |
| 内存逃逸 | 哪些变量会逃逸？怎么优化？ | Reconcile 里返回给外层的对象可能逃逸；局部变量不一定在栈上 |
| channel | channel 和锁的区别？带缓冲 vs 无缓冲？ | WorkQueue 内部用带缓冲 channel + cond；分发用 gRPC 流 |
| context | context 怎么取消？ | **最硬的点**：onLoseLeader 用 context.WithCancel 取消 leader 专属循环——这是我在 P1-B2 真实用到的 ctx 取消 |
| 并发安全 | 哪些是 goroutine-safe 的？ | Informer 本地缓存 + 内存注册表用的锁；WorkQueue.GetCtx(ctx) 解决 sync.Cond 不响应取消 |

**加分叙事**：WorkQueue 基于 sync.Cond 的 Get() 不响应 ctx 取消 → 我改成 GetCtx(ctx) → Leader 失权瞬间 reconciler 退出。这是"Go 并发细节真的影响分布式正确性"的实锤。

## 三、分布式（必考，Dolphin 弹药最足）

| 考点 | 高频问法 | 贴回 Dolphin 怎么讲 |
|------|---------|-------------------|
| 分布式锁 | Redis 锁 vs DB 乐观锁？key 怎么设计？ | 讲 Dolphin 选主不是"拿锁"而是"Lease 过期写入被拒"；对比 Redis 锁过期后旧持有者还能写 |
| CAP | 解释 CAP？etcd 是哪类？ | etcd 是 CP；分区时少数派无法提交，可能短暂无主而非双主 |
| 一致性模型 | 最终一致 vs 强一致 | Worker 注册表"读库 vs 读内存"不一致的 bug → 统一到内存注册表（P1-B2 证据 2d） |
| 选主 | etcd 选举原理？ | Campaign key 由 leaseID 唯一确定 + waitDeletes 按 create_revision 全序，数学上不可能双主 |
| 幂等 | 什么是幂等？怎么做？ | P1-B3：instance_id 唯一化 + 心跳超时重分发；至少一次 + 幂等 |
| 故障转移 | 怎么检测故障？转移多久？ | 心跳滑动窗口 + Lease；硬数据分布（P1-B2/P1-B3） |
