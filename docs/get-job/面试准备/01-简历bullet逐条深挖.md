## P1-B1 ｜ 控制器模式（事件驱动调度）

**Bullet 原文**
> 借鉴 K8s 控制器模式，用 Informer 本地缓存 + WorkQueue 限速重试 + Reconcile 持续协调实现事件驱动调度，替代定时扫库；实测调度延迟 P50 约 1.4s / P99 约 2s，Reconciler 读本地缓存不查库，任务数增长不放大数据库压力。

**对应岗位问题**：证明理解现代分布式系统设计（K8s 模式），不只会调框架；Go 并发与缓存一致性。

**30 秒讲法**
"调度核心不是定时扫数据库，而是控制器模式：Informer 每 1 秒把数据库变更同步进本地缓存，任务到期入 WorkQueue，Reconciler 循环持续协调——从本地缓存读任务、不查库。实测调度延迟 P50 约 1.4 秒，这个延迟来自 Informer 的 1 秒轮询间隔，我有清晰的延迟来源认知。"

**60–90 秒展开版**
- 背景：定时扫库方案有两个问题：到期扫描 O(N) 全表扫 + 时间窗滞后；任务多时数据库压力随任务数线性涨。
- 我做了什么：套用 K8s 控制器三件套——Informer 维护本地缓存（增量同步）、WorkQueue（限速重试 + 幂等去重）、Reconcile 持续协调（不假设"调用一次就成功"）。
- 取舍：选 1s 轮询 Informer 而不是 etcd watch 事件驱动，是为了简单可靠（watch 要处理断连重放）；代价是延迟天花板 1s。如果接 etcd watch 可降到毫秒级——我知道这个 trade-off。
- 结果：100 个任务批量触发时，Reconciler 全从本地缓存读，数据库查询量不随任务数增长。

**面试官可能怎么问**
1. Informer 和普通缓存有什么区别？缓存和数据库一致吗？
2. 为什么 WorkQueue 要限速重试？失败多少次会放弃？
3. 为什么不直接用 etcd watch？事件驱动不是更快吗？
4. 本地缓存怎么保证不读脏数据？多个 scheduler 并发时怎么办？

**必须讲清的事实**：Informer 轮询间隔 1s（代码里的轮询周期）；WorkQueue 限速参数；Reconciler 从缓存读、不查库。

**证据口径**：58 样本直方图 `dolphin_scheduler_task_lag_seconds`，P50 1.37s / P95 1.94s / P99 2s。样本=100 个 `*/1` 任务自然触发。

**二三层追问 + 兜底**
- "WorkQueue 失败重试的退避怎么配？"→ 讲 RateLimitingQueue 概念 + 指数退避；细节记不准就讲设计意图。
- "缓存一致性怎么保证？"→ Informer 每周期全量比对 + 事件触发；若被追"极端不一致窗口"，诚实说"这是设计取舍，极端场景我会加 watch 兜底"。

**不能说什么**：不说"延迟 1s 已经很快"这种无依据结论；不吹"毫秒级事件驱动"（实际是轮询）。

**处理策略**：放大。这是 Go 并发 + 分布式系统双靶心的核心展示位。

## P1-B2 ｜ etcd 选主 + Lease 防脑裂

**Bullet 原文**
> 基于 etcd Lease 实现多调度器选主，Lease 过期后旧主写入被拒绝，从机制上杜绝脑裂；实测 Leader 故障接管 N=10：11.2–15.64s（中位 13.35s），全部落在 [10,15]s 理论窗口，证明是真租约选举而非心跳判活。

**对应岗位问题**：分布式一致性、CAP、选主/故障转移、分布式锁——Go 后端岗位题最高频的板块。

**30 秒讲法**
"调度器高可用我用 etcd 选主。关键不是'拿到锁'，而是旧 Leader 的 Lease 过期后，它的 etcd 写入会被拒绝——这是 Redis 锁做不到的，从机制上杜绝脑裂。Leader 故障接管不是一个单点数字，而是一个分布：Lease TTL 15 秒、每 5 秒续约，所以 kill 时刻租约剩余 10–15 秒。我跑 10 次，min 11.2 / median 13.35 / max 15.64 秒，全落在理论窗口 [10,15] 秒内——这证明我用的是真租约选举。"

**60–90 秒展开版**
- 为什么 etcd 不用 Redis 锁：Redis 锁过期后旧持有者还能继续写（无法强制），etcd 的 Lease 过期后旧主的 Put 返回 `ErrLeaseNotFound`，写入被机制性拒绝。这就是"防脑裂"的机制层保证。
- 选主实现：`concurrency.Election.Campaign`，竞选 key 由 leaseID 唯一确定（etcd v3.7.1），`waitDeletes` 按 create_revision 全序等待，只有最小者胜出——数学上不可能双主。
- 数据：10 次 kill 接管，全落 [TTL−TTL/3, TTL]=[10,15]s + 约 1s 测量开销。租约选举的指纹：心跳判活能做到秒级，租约必须等过期，且过期剩余时间随续约相位波动。

**面试官可能怎么问**
1. Redis 分布式锁和 etcd 选主有什么区别？为什么这里选 etcd？
2. Lease 的 TTL 怎么定？太长/太短分别有什么问题？
3. 两个 scheduler 同时认为自己是 Leader 可能吗？（假脑裂故事）
4. CAP 里 etcd 是哪一种？网络分区时选主会怎样？

**必须讲清的事实**：TTL=15s、续约间隔 TTL/3=5s；理论窗口推导；旧主写入返回 ErrLeaseNotFound。

**证据口径**：`hack/failover_test.ps1 -Runs 10`。分布 min 11.2 / median 13.35 / mean 14 / max 15.64s，全在 [10,15]s + 测量开销内。

**二三层追问 + 兜底**
- "TTL 定 15 秒的依据？"→ TTL 要远大于续约间隔（15/5=3 倍）+ 覆盖调度周期；短了频繁切换、长了故障转移慢。
- "网络分区时选主会怎样？"→ etcd 是 CP（多数派）；分区后少数派无法提交、选举可能重新进行；诚实讲"极端分区下可能出现短暂无主，而不是双主"。

**不能说什么**：不说"绝对不会脑裂"这种绝对话术——讲"机制上杜绝 + 实测分布支撑"；不背单点 15s，讲分布。

**处理策略**：放大。这是分布式一致性靶心的核心弹药，也承接假脑裂 STAR 故事（见 `04`）。

## P1-B3 ｜ 幂等 instance_id + 不丢不重

**Bullet 原文**
> 以幂等 instance_id + 心跳超时重分发实现任务不丢不重；实测 Worker 故障恢复 N=5：22.68–29.4s（符合 [21,36]s 滑动窗口理论区间），幂等 5 次全 PASS，无重复 instance_id。

**对应岗位问题**：至少一次语义、幂等设计、任务可靠性——区分"会写 CRUD"和"理解分布式语义"的关键。

**30 秒讲法**
"Worker 执行到一半挂了，任务不能丢也不能重。我用幂等 instance_id——每次执行尝试一个唯一 ID，重试生成新的 instance_id，旧实例即使残留也不会被误判为成功。Worker 判定用心跳滑动窗口：心跳间隔 10 秒、超时 30 秒，恢复时间 = 30 − kill 距上次心跳 + 检测周期。5 次实测 22.68–29.4 秒，全部小于 30 秒，正好证明判定基于 last_heartbeat 滑动窗口而不是从 kill 时刻起算。"

**60–90 秒展开版**
- 语义：每个执行尝试有唯一 instance_id；重试产生新 ID；旧实例残留不影响结果判定。实测 5 次 kill，最终 `success 3 / failed 5 / running 2`：5 次 kill 各产生 1 条 failed（被杀实例）+ 1 条新实例（恢复），无重复 instance_id = 不重，5 failed + 5 恢复 = 不丢。
- 滑动窗口细节：heartbeat 每 10s 上报，超时阈值 30s。kill 前最后一次心跳后 last_heartbeat 就停止更新，所以恢复总是 < 30s，理论区间 [21,36]s。

**面试官可能怎么问**
1. instance_id 怎么生成的？怎么保证全局唯一？
2. "不丢不重"具体靠哪两个机制配合？只靠幂等够吗？
3. 心跳超时 30s，任务会不会被重复执行（旧 worker 还活着）？
4. 至少一次 vs 恰好一次，你实现的是哪种？

**必须讲清的事实**：instance_id 生成方式（如 UUID）；心跳/超时参数；恢复时间推导；幂等验证方法（查 TaskLog 无重复 instance_id）。

**证据口径**：`failover_test.ps1 -WorkerRuns 5`。恢复分布 min 22.68 / median 27.4 / mean 26.86 / max 29.4s，全部 < 30s，落 [21,36]s 理论区间。

**二三层追问 + 兜底**
- "怎么防止旧 worker 没死透导致双执行？"→ 诚实讲：靠心跳超时 + instance_id；极端网络分区下是"至少一次"语义，可能短暂双执行但结果幂等。这是权衡，讲清即可。
- "TaskLog 怎么验证不重复？"→ 按 instance_id 去重计数，5 次跑无重复。

**不能说什么**：不说"保证恰好一次"（实际是至少一次 + 幂等）；不吹"永不丢失"。

**处理策略**：放大。对"至少一次 / 幂等"这种面试高频概念有实锤。

## P1-B4 ｜ Redis Lua 分布式限流

**Bullet 原文**
> 用 Redis + Lua 原子令牌桶实现多实例共享的分布式限流；实测 15000 请求中 429 数量与理论超限值精确吻合，避免「各实例独立限流导致总量翻倍」。

**对应岗位问题**：Redis 使用深度、原子性、分布式状态共享——存储与缓存靶心。

**30 秒讲法**
"多网关实例要共享限流状态，我用 Redis 令牌桶，Lua 脚本保证原子性。vegeta 打 1000 QPS、rate=100，实测 15000 个请求里 429 的数量与理论超限值吻合。关键点是限流状态在 Redis、多个实例共享同一个桶，不会出现'各实例独立限流导致总量变成 2×rate'。"

**60–90 秒展开版**
- 为什么 Lua：令牌桶的取令牌 + 扣减必须是原子的，多实例并发访问 Redis，用 Lua 把判断和扣减包成一个原子操作，避免并发读改写竞态。
- 为什么共享：单实例本地限流在扩容后会总量翻倍；共享桶保证集群总量精确 = rate。
- 数据口径：15000 请求中 13300 个 429、1700 个 200（≈100/s × 15s + 200 突发）。

**面试官可能怎么问**
1. 令牌桶和漏桶区别？为什么选令牌桶？
2. Lua 脚本在 Redis 里怎么保证原子性？不原子会怎样？
3. Redis 挂了限流怎么办？（降级策略）
4. 限流的 key 怎么设计？怎么区分用户/IP/总量？

**必须讲清的事实**：rate=100、打 1000 QPS、15000 请求；429/200 的构成（100/s×15s + 突发）。

**证据口径**：vegeta 压测 15000 请求。⚠️ 若被追问"具体 13300/1700"，记不清就模糊化为"429 数量与理论超限值吻合"。

**二三层追问 + 兜底**
- "Redis 故障时限流降级吗？"→ 诚实讲当前实现（若 Redis 不可用则放行或拒绝）；"fallback 是监控 + 告警，这是可改进点"。
- "为什么 429 是 13300 不是 14900？"→ 因为 rate=100 允许 100/s 通过 + 令牌桶有突发容量，200 是合法放行量。讲清原理即可，不必背精确数。

**不能说什么**：不报"13300/1700"若没把握；不说"高可用"（Redis 单点这是弱点，被问到就诚实）。

**处理策略**：正常讲。若口径记不牢，简历和口头都模糊化到"429 与理论超限吻合"。

## P1-B5 ｜ Worker 自动跟随 Leader（服务发现）

**Bullet 原文**
> Worker 通过 etcd watch 动态发现当前 Leader 并自动切换连接（实测 4s 重连），配合 Leader 周期性重发布 + 连接失败 ResolveNow 兜底，故障转移链路端到端闭环。

**对应岗位问题**：服务发现、gRPC 连接管理、etcd watch、故障转移链路的完整性。

**30 秒讲法**
"Worker 不硬编码 Scheduler 地址，而是通过 etcd 发现当前 Leader：Leader 当选后把 gRPC 地址写入 etcd（绑定选主 Lease，Leader 死亡自动过期），Worker watch 到变化就切换连接，实测 kill Leader 后 4 秒内自动重连。另外我做了双保险：Leader 每 5 秒周期重发布地址，Worker 连接失败且退避 ≥8 秒时主动 ResolveNow 重新解析——即使 watch 事件丢了也能自愈。"

**60–90 秒展开版**
- 背景：早期版本 Worker 把 Scheduler 地址写死在配置里，Leader 从 50051 切到 50052 后 Worker 连不上新主，故障转移链断掉——这是"选主做了但链路没闭环"的典型坑。
- 三层保障：① Leader 把地址写 etcd（key 绑 Lease）；② Leader 周期性重发布防 key 意外过期；③ Worker 连接失败退避达阈值触发 ResolveNow 主动 Get。

**面试官可能怎么问**
1. 为什么不用固定地址 + 反代？
2. watch 事件丢了怎么办？ResolveNow 的触发条件？
3. leader-addr 这个 key 怎么绑定 Lease 的？Leader 死后 key 多久消失？

**必须讲清的事实**：key 路径（/dolphin/scheduler/leader-addr）；重发布周期 5s；ResolveNow 阈值 8s；实测 4s 重连。

**证据口径**：kill Leader 后 Worker 经 etcd watch 自动切到新端口，实测 4s（单次实测，⚠️ 样本少，可模糊为"秒级"）。

**二三层追问 + 兜底**
- "4 秒怎么测的？"→ 单次观测值；记不牢就模糊"秒级"。若面试官追样本，诚实说"这个指标我采集的样本少，改简历时可以再补一组"。

**不能说什么**：不吹"watch 不会丢事件"——你恰恰做了兜底；不硬报 4s 单点。

**处理策略**：正常讲。体现"故障转移链路闭环"的工程完整度，是二面"项目深度"的加分点。

## P1-B6 ｜ Prometheus 埋点 + 故障注入测试

**Bullet 原文**
> 全链路 Prometheus 埋点（调度延迟/选主状态/队列深度/worker 在线数）+ 故障注入测试体系（kill leader / kill worker / 慢任务）；go test -race 全过，Windows 交叉编译通过。

**对应岗位问题**：工程与交付能力、可观测性、测试体系——虾皮二面"有没有做过集群部署/监控系统"的反打点。

**30 秒讲法**
"我给整个系统做了 Prometheus 埋点：调度延迟、选主状态、队列深度、worker 在线数这些黄金信号。围绕它们我搭了故障注入测试体系——kill leader、kill worker、跑慢任务——用来验证故障转移链路端到端闭环。另外单测跑 go test -race，编译做 Windows 交叉编译验证。"

**60–90 秒展开版**
- 指标清单：`dolphin_scheduler_task_lag_seconds`（调度延迟）、`dolphin_scheduler_is_leader`（选主状态）、队列深度、worker 在线数。这些是"能回答系统现在行不行"的信号，不是装饰。
- 故障注入：failover_test.ps1 自动化 kill leader/kill worker 并采集接管/恢复分布——面试硬数据就是从这套体系出来的。
- 排障方法论：假脑裂事件（见 `04`）教会我"先确认系统坏了还是仪表盘错了"——指标读法本身也可能错。

**面试官可能怎么问**
1. 埋了哪些指标？为什么选这些？
2. 故障注入脚本怎么设计的？怎么保证测试可信？
3. 遇到过一个和监控有关的疑难问题吗？（假脑裂 STAR 故事入口）
4. 压测怎么做的？vegeta 的指标怎么解读？

**必须讲清的事实**：指标清单、故障注入命令（kill 哪个进程、怎么采数）、`go test -race`、Windows 交叉编译命令。

**证据口径**：埋点代码在 dolphin 仓库；故障注入由 `hack/*.ps1` 自动化；压测数据见 `docs/benchmark.md`。

**二三层追问 + 兜底**
- "假脑裂具体怎么回事？"→ 用 STAR 故事（`04`）：测出双主 + 1.17s 接管 → 不急着改代码 → 读 etcd 源码确认不可能双主 → dump etcd 验证单主 → 定位测试脚本子串匹配命中 HELP 行 → 行首锚定修复，接管回到 11.2–15.64s。
- "如果指标显示 429 异常怎么排查？"→ 从限流桶状态 → Redis → 流量来源逐层查。

**不能说什么**：不把"埋点"说成"监控平台"（超出实际）；不吹告警体系（如果没做）。

**处理策略**：放大。这是工程与交付靶心的核心，也是"集群/监控/故障排查"隐性门槛的反打点。
