## 一、项目三层深挖（二面重头戏）

面试官会顺着简历追三层。每一层都要有实物：

**第一层：这是做什么的？**
Dolphin 是受 K8s 控制器模式启发的 Go 分布式定时任务调度平台：Gateway（API 面）/ Scheduler（控制面）/ Worker（执行面），etcd 选主 + MySQL 持久化 + Redis 限流。

**第二层：怎么做的？（每个设计都有 trade-off）**
| 设计 | 为什么这么选 | 不选什么 |
|------|-------------|---------|
| Informer 轮询 1s | 简单可靠、延迟可接受 | etcd watch（要处理断连重放，延迟可降到毫秒但复杂） |
| etcd Lease 选主 | 旧主过期后写入被拒，机制防脑裂 | Redis 锁（过期后旧持有者还能写） |
| 内存注册表选 Worker | "能选中"和"能下发"绑同一份数据 | 读 MySQL + 写内存（数据源不一致导致毒化） |
| Redis Lua 令牌桶 | 原子性 + 多实例共享 | 本地限流（扩容后总量翻倍） |

**第三层：难点和取舍？（追问不崩）**
- 假脑裂排障：观测手段错 vs 系统错 → 先怀疑仪表盘。
- 失权即停：选主只是第一步，Lease 丢失瞬间 leader 循环必须被 context 取消，否则业务层双写。
- 至少一次 + 幂等：不是"恰好一次"；极端网络分区可能短暂双执行但结果幂等。

## 二、集群部署 / 监控 / 压测叙事（反打"没做过集群"的弱点）

> 虾皮二面问"有没有做过集群部署、有没有做过监测系统"。你的答案：

"我没有在大规模生产集群上部署过，但在 Dolphin 里我真实做了这两件事：双 scheduler 用 etcd 选主组成高可用集群，我验证过 Leader 故障转移 10 次，接管时间全落在 11.2–15.64 秒的理论窗口；Worker 集群里 kill 一个，任务 22.68–29.4 秒内在另一个 worker 恢复，幂等验证通过。监控我给整个系统埋了 Prometheus 指标——调度延迟、选主状态、队列深度、worker 在线数——故障注入脚本就是靠这些指标判断系统状态的。"

> 关键：承认"没上过生产集群"不丢分，但要说清"我在自建系统里把集群语义真实跑通了、还有数据"。这比空口说"了解集群"强。

## 三、AI 编程协作边界（必被追问，诚实边界是加分项）

**高频问法**："Dolphin 是你写的还是 AI 写的？""AI 帮你写了多少？""怎么保证 AI 不是照抄代码？"

**标准回答**（真实、不装资深）：
"我用 AI 做辅助实现，但架构和验收是我自己做的。具体分工：整体架构、模块划分、技术选型——比如选 etcd 不选 Redis 锁、选 Informer 不选扫库——这些决策是我做的，我能讲清每个 trade-off。AI 帮我加速写样板代码、查 API 用法、写测试。但我做了三件事保证代码可信：① 每段 AI 生成代码我都 review 并改过；② 关键正确性靠测试验证——故障转移、幂等这些不是'看起来能跑'，是我用故障注入实测出来的分布数据；③ 踩坑复盘我自己做，比如假脑裂那个 bug 就是我自己定位的。"

**要点**：不把 AI 辅助说成独立开发，但强调"决策权在自己"。面试官要的不是否认 AI，是确认你有判断力。

## 四、STAR 故事：「假脑裂」排障（备用难题）

**S（情境）**：写 Leader 故障转移测试时，测出两个 scheduler 同时报 is_leader=1，接管只要 1.17 秒——看起来像严重脑裂。
**T（任务）**：判断是选主逻辑真错了（真脑裂），还是观测手段出了问题（假象）。这决定改选主代码还是改测试脚本。
**A（行动）**：没急着改代码，先做三件事：① 通读 etcd v3.7.1 concurrency 源码，确认竞选 key 由 leaseID 唯一确定、waitDeletes 按 create_revision 全序等待——etcd 层数学上不可能双主；② dump etcd 实际状态，任意时刻只有 1 个 leader key、1 个 lease；③ 回头查测试脚本，发现读 Prometheus 指标用子串匹配，命中了 `# HELP ... is_leader 1` 帮助行文字，把 is_leader 永远读成 1。
**R（结果）**：改行首锚定后假双主消失，接管时间回到 11.2–15.64s 理论窗口。从此记住：分布式系统排障第一步是确认"系统真的坏了"还是"仪表盘读错了"。

> 同时打两个方向：Go 后端展示"能读 etcd 源码定位问题"；SRE 展示"排障方法论"。
